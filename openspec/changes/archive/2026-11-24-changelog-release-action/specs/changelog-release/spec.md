## Purpose

Publish a GitHub Release from a checked-out release catalog so consumer projects can reuse tag, notes and asset publishing without depending on the changelog-generation Action.

## ADDED Requirements

### Requirement: Standalone catalog selection
The Action SHALL require an explicit `version` and SHALL read `catalog-path` relative to the checked-out repository root, defaulting to `changelogs.json`. It SHALL NOT depend on the changelog-generation Action, its outputs or a specific GitHub event. It SHALL select exactly one record matching the version and require `notes.en` to be a non-empty array of non-empty strings. It SHALL format those entries as Markdown bullets.

#### Scenario: Release generated by another process
- **WHEN** a caller supplies a compatible catalog and explicit version without invoking the changelog-generation Action
- **THEN** the Action reads and formats the matching English notes

#### Scenario: Missing version
- **WHEN** the `version` input is missing or blank
- **THEN** fail before creating a tag or Release and explain that an explicit version is required

#### Scenario: Missing, duplicate or invalid catalog record
- **WHEN** the catalog has no unique record matching the version or its `notes.en` value is invalid
- **THEN** fail before creating a tag or Release

### Requirement: Create and publish a versioned Release
The Action SHALL create a `v{version}` tag targeting the checked-out commit and a GitHub Release named `v{version}` whose body contains the formatted English notes. It SHALL create the Release as a draft, upload all requested assets, and publish it only after every upload succeeds. It SHALL require `GITHUB_TOKEN` with `contents: write`. If the version tag or any Release already exists, it SHALL fail without modifying the existing tag or Release.

#### Scenario: Publish a Release without assets
- **WHEN** the catalog entry is valid and no tag or Release exists for the version
- **THEN** create the tag at the checked-out commit, publish the Release with the English notes, and return its URL

#### Scenario: Existing tag or Release
- **WHEN** the version tag or a draft or published Release already exists
- **THEN** fail without changing it or creating another Release

#### Scenario: Release API failure
- **WHEN** GitHub rejects creation or publication
- **THEN** fail the Action and report the API error

### Requirement: Validate and upload multiple assets
The Action SHALL accept an optional newline-separated list of repository-relative file paths. It SHALL allow multiple regular files, reject paths outside the repository and duplicate asset filenames, and validate every requested file before creating a tag or Release. It SHALL upload every validated file to the same draft Release. If an upload fails, it SHALL fail and leave the Release unpublished.

#### Scenario: Upload multiple files
- **WHEN** multiple valid files are supplied
- **THEN** upload each file to the same Release before publishing it

#### Scenario: Invalid asset path
- **WHEN** any requested file is missing, is not a regular file, escapes the repository root or collides by filename
- **THEN** fail before creating a tag or Release

#### Scenario: Asset upload fails
- **WHEN** GitHub rejects an asset upload after creating the draft Release
- **THEN** fail and leave that Release unpublished

### Requirement: Return successful release outputs
After publishing the Release, the Action SHALL return `notes-en`, `tag-name` and `release-url`. It SHALL NOT report successful release outputs when publication fails.

#### Scenario: Release succeeds
- **WHEN** the tag, Release and all requested assets are published successfully
- **THEN** return the formatted notes, `v{version}` tag name and published Release URL

#### Scenario: Release fails
- **WHEN** any validation, tag, Release or asset operation fails
- **THEN** fail the Action without reporting a published Release URL
